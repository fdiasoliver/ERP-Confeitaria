# ADR-005 — Padrão Oficial de Identificadores (IDs)

**Status:** Aprovado  
**Data:** 02/07/2026  
**Sprint:** 2.0.8  
**Proposto por:** Doce Menina — Decisão arquitetural de fundação  
**Aprovado por:** Usuário (proprietário do produto)

---

## Contexto

O ERP Doce Menina possui 20+ modelos persistentes no banco de dados PostgreSQL (Supabase). Cada modelo precisa de um identificador único para:

- relacionamentos entre entidades (chave estrangeira);
- operações REST (GET, PATCH, DELETE `/api/admin/recurso/:id`);
- rastreabilidade em logs e auditorias;
- sincronizações futuras entre ambientes (dev → staging → prod).

Antes desta ADR, o padrão estava implícito na seção 10 do PROJECT_GOVERNANCE.md e nas convenções de Prisma, mas não havia sido formalizado como decisão inegociável.

---

## Decisão

**Todos os modelos persistentes do ERP Doce Menina utilizarão obrigatoriamente:**

```prisma
id String @id @default(cuid())
```

Esta decisão é válida para qualquer entidade nova ou existente, em qualquer módulo (2.A–2.L e além), sem exceção — salvo nova ADR aprovada explicitamente.

---

## Justificativa técnica

| # | Motivo | Detalhe |
|---|--------|---------|
| 1 | **Compatibilidade nativa com Prisma** | `cuid()` é gerado pelo Prisma Client, sem extensão de banco, sem configuração adicional |
| 2 | **Integração com PostgreSQL/Supabase** | Armazenado como `TEXT`, sem impacto em índices; totalmente compatível com o provedor utilizado |
| 3 | **Globalmente único** | Colisões entre registros gerados em momentos ou ambientes distintos são estatisticamente impossíveis |
| 4 | **Preparado para integrações futuras** | APIs externas (WhatsApp, PIX, Google Maps) e webhooks podem usar o `id` como referência sem risco de colisão |
| 5 | **Adequado para APIs REST** | `/api/admin/produtos/cm3x9z2...` é opaco, seguro e padronizado — sem vazamento de informação de negócio |
| 6 | **Evita colisões entre ambientes** | Um registro criado em dev tem o mesmo `id` ao ser promovido para produção, sem conflito de sequência |
| 7 | **Permite sincronizações futuras** | Exportação, importação e migração de dados entre bancos sem necessidade de remapeamento de IDs |
| 8 | **Independe de sequência numérica** | Não requer lock no banco para gerar o próximo valor; escala horizontalmente sem coordenação |
| 9 | **Não expõe quantidade de registros** | `id: "cm3x9z2..."` não revela quantos pedidos existem, diferente de `id: 1247` — protege informação competitiva |

---

## Alternativas rejeitadas

| Alternativa | Motivo da rejeição |
|-------------|-------------------|
| `Int @default(autoincrement())` | Expõe volume de registros; cria dependência de sequência de banco; falha em sincronizações multi-ambiente; incompatível com sharding futuro |
| `UUID` misturado com `CUID` | Dois padrões no mesmo projeto geram inconsistência e confusão. UUID v4 é completamente aleatório (pior indexação que CUID); UUID v7 exige configuração extra |
| `NanoID` | Não é nativo do Prisma; exige geração no código da aplicação com possibilidade de colisão sem implementação cuidadosa |
| `ULID` | Não suportado nativamente pelo Prisma `@default()`; exige geração manual; introduce complexidade sem benefício concreto |
| `KSUID` | Sem suporte nativo no Prisma; dependência de biblioteca externa; sem vantagem sobre CUID para este projeto |

## Padrão obrigatório

### Regra 1 — Relacionamentos exclusivamente por `id`

Todo relacionamento entre entidades utilizará exclusivamente o campo `id` (CUID gerado pelo Prisma). Nenhum relacionamento (`@relation`) pode usar `slug`, `orderNumber`, `name` ou qualquer outro campo como chave técnica de vínculo.

```prisma
// ✅ CORRETO
model Product {
  id         String          @id @default(cuid())
  categoryId String
  category   ProductCategory @relation(fields: [categoryId], references: [id])
}

// ❌ PROIBIDO
model Product {
  slug         String
  categorySlug String
  category     ProductCategory @relation(fields: [categorySlug], references: [slug])
}
```

### Regra 2 — `slug` não é chave técnica

`slug` **nunca** pode ser utilizado como chave de relacionamento (`@relation`, `@unique` com função de FK, ou parâmetro de busca interna entre entidades).

### Regra 3 — Propósito exclusivo do `slug`

`slug` existe exclusivamente para:

- URLs amigáveis (ex: `/vitrine/bolos-de-aniversario`)
- SEO e indexação por mecanismos de busca
- Navegação pública (filtros de vitrine, links compartilháveis)
- Filtros públicos em APIs (ex: `GET /api/products?category=bolos`)

Internamente, toda lógica de negócio, todos os joins e todas as referências entre entidades usam `id`.

### Regra 4 — IDs não são informação de negócio

IDs nunca devem ser exibidos ao usuário como informação de negócio. O número de um pedido visível ao cliente é `orderNumber` (sequencial, para uso humano); o `id` é estritamente técnico e interno. Nenhuma interface deve mostrar, copiar ou exportar `id` como referência de negócio para o usuário final.

## Exceções documentadas

As seguintes situações são permitidas e **não contradizem esta ADR**:

### Exceção E1 — `orderNumber` como número de exibição

O modelo `Order` possui `orderNumber Int @unique @default(autoincrement())`. Este campo é um **número sequencial para exibição humana** (ex: "Pedido #47"), **não é a chave primária**. A PK continua sendo `id String @id @default(cuid())`. Esta coexistência é válida e não configura exceção à ADR.

### Exceção E2 — PK composta em tabelas de junção implícitas

Tabelas de junção many-to-many sem semântica própria (ex: `ProductOccasion`) podem usar `@@id([fk1, fk2])` como chave primária composta, pois não possuem identidade de negócio independente. Esta exceção **não se aplica** a entidades com semântica própria.

## Escopo e vigência

- **Escopo:** todos os modelos Prisma do ERP Doce Menina, presentes e futuros.
- **Vigência:** imediata a partir de 02/07/2026.
- **Módulos impactados:** todos os módulos 2.C–2.L ainda não implementados estão obrigados a seguir este padrão. Os módulos já implementados (2.A, 2.B) já estão em conformidade.

## Impacto arquitetural

| Camada | Impacto |
|--------|---------|
| `schema.prisma` | Padrão já aplicado em todos os modelos existentes. Novos modelos devem seguir obrigatoriamente. |
| `src/lib/types.ts` | Interfaces TypeScript usam `id: string` (CUID como string). Sem mudança necessária. |
| `src/lib/repositories/` | Busca por `id` via `prisma.model.findUnique({ where: { id } })` é o padrão. |
| `src/app/api/` | Parâmetros de rota dinâmicos `[id]` correspondem ao CUID. |
| Front-end | IDs não são exibidos. `orderNumber` é o identificador visível ao usuário. |
